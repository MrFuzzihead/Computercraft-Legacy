# Codebase Analysis Report

> **Scope:** Full review of `src/main/java` (368 Java files), `src/main/resources` (ROM Lua), and the build/test setup of this decompiled-and-patched ComputerCraft 1.7.10 fork (Cobalt runtime, CustomNPCs compat, ChatBox/Speaker/NPC peripherals, Redstone Relay, WebSocket/TTS additions).
> **Method:** Static review of core runtime (`core/`), shared Minecraft-coupled code (`shared/`), client code, compat layer, ROM `bios.lua`, plus selected comparison against the original dan200/ComputerCraft 1.7.10 source (commit `bbe7a4c`) to distinguish inherited legacy issues from fork regressions.
> Severity legend: 🔴 High (crash / exploitable), 🟠 Medium (functional bug / real DoS risk), 🟡 Low (hardening / quality), 🔵 Info.

---

## Executive summary

The codebase is in good shape overall. The **custom additions** (Speaker + DFPWM/PCM audio, ChatBox, NPC Detector/Interface/Trader, Redstone Relay, WebSocket API, seekable `fs` handles, `os.date`, palette support) are consistently well-written: main-thread execution via `executeMainThreadTask`, snapshot-based event dispatch, careful argument validation, and a solid 49-file unit-test suite. Most severe problems are **inherited from upstream CC 1.7.10** and remain unfixed — notable because this fork's stated purpose is bug-fixing. The most impactful items:

1. 🔴 ~~Unvalidated packet lengths in `ComputerCraftPacket.fromBytes` → a modified client can OOM-crash a server with one tiny packet.~~ **FIXED** (see S1 — validation + caps + tests added)
2. 🔴 ~~**Unbounded HTTP**: no request cap, no download-size cap, default whitelist `*` → any player can exhaust server memory/threads.~~ **FIXED** (see S2 — `http_max_requests`/`http_max_websockets`/`http_max_download`/`http_blacklist` + tests)
3. 🔴 ~~**`NBTUtil.toNBTTag` encodes the map *key* as the *value*** → table-valued event arguments sent client→server are silently corrupted; plus unbounded `new Object[len]` from client NBT.~~ **FIXED** (see S3 — key/value fix, `len` derives from written entries, `byte[]` support, hostile-length clamps + tests)
4. 🟠 **Redstone Relay mutates the world from the computer thread** (off-main-thread neighbor notifications).
5. 🟠 ~~**`buffer` API is dead code** (never registered) and contains two genuine bugs.~~ **RESOLVED** (see B1 — deleted as not-a-CCTweaks-feature; `TextBuffer.fill` empty-pattern div-by-zero fixed + tested)
6. 🟠 ~~`ComputerThread` concurrency hazards (unsynchronized `WeakHashMap`, silently dropped tasks) and a globally serialized, thread-per-task execution model.~~ **ALL FIXED** (see C1, C2 and P1 — worker pool with per-computer lanes, watchdog timeout enforcement, `computerThreads` config).

## 1. Security & crash findings

### S1 🔴 Unvalidated lengths in `ComputerCraftPacket.fromBytes` → server OOM — ✅ **FIXED**
`shared/network/ComputerCraftPacket.java` lines 111–157 (original):

```java
int len = buffer.readInt();
byte[] b = new byte[len];          // line 116 — no bound vs buffer.readableBytes()
...
this.m_dataByte = new byte[nByte][];   // line 141
int length = buffer.readInt();
this.m_dataByte[kx] = new byte[length];
...
byte[] bytes = new byte[byteLength];   // line 157
```

Every length field is attacker-controlled and allocated **before** any readability check. A malicious client can send a ~20-byte packet declaring `len = 0x7FFFFFFF`, causing a multi-GB allocation → `OutOfMemoryError`. Because `PacketHandler` catches `Exception` (not `Throwable`), the `Error` escapes and can take down the netty thread / server. This is a known legacy-CC 1.7.10 attack vector; it is inherited from upstream but is the single most important fix for any public server.

**Fixed (2026-06):** every declared length/count is now validated via a `checkLength()` helper before any allocation — it must be non-negative, within an absolute cap, and no larger than `buffer.readableBytes()` — otherwise a `DecoderException` (a `RuntimeException`, so it is caught by `PacketHandler`) is thrown without allocating. Caps: 64 strings / 64 ints / 64 byte arrays (array length ≤ 1 MiB each), strings ≤ 1 MiB, NBT ≤ 4 MiB. These are far above any legitimate payload (speaker audio ≤ 128 KiB, terminal NBT ≤ ~50 KiB). The count reads were also switched from signed `readByte()` to `readUnsignedByte()` so counts can no longer go negative. Covered by `src/test/java/dan200/computercraft/shared/network/ComputerCraftPacketTest.java` (round-trips for empty/full/speaker-audio/terminal-NBT packets plus rejection tests for every malicious-length variant).

### S2 🔴 HTTP API is unbounded (memory + thread DoS) — ✅ **FIXED**
* `core/apis/HTTPAPI.java:210` — `m_httpRequests` grows without limit; there is no `http_max_requests` equivalent. Every `http.request` spawns a **new thread** (`HTTPRequest` constructor), so a Lua program can spawn thousands of concurrent threads.
* `core/apis/HTTPRequest.java:198` — the download loop reads the response into memory with **no size cap** (`http_max_download` equivalent missing). A malicious/Lua-initiated download of a huge file (or a server that never closes the stream) OOMs the server; with `timeout = 0` (the default when no timeout arg is given) there is not even a read timeout.
* `ComputerCraft.java:106` — `http_whitelist = "*"` by default: every computer can talk to the entire internet. There is also **no blacklist** (`http_blacklist` equivalent) — not possible to deny specific hosts while allowing the rest.

**Fixed (2026-06):** four new config options (all `general` section, in `ComputerCraft.java`):

| Option | Default | Meaning |
|---|---|---|
| `http_max_requests` | 16 | Max in-flight HTTP requests per computer; `0` = unlimited |
| `http_max_websockets` | 4 | Max open/pending websockets per computer; `0` = unlimited |
| `http_max_download` | 16 MiB | Max response body; oversized bodies are aborted (early via `Content-Length`, and during streaming) and surface as `http_failure(url, "Download limit exceeded", nil)` |
| `http_blacklist` | (empty) | Semicolon-separated wildcard domains blocked even if whitelisted; applied to both `http` and websocket URLs |

Caps are enforced under the tracking list's lock in `HTTPAPI.callMethod`, before the worker thread is started; an over-cap `http.get/post` returns `nil, "Too many ongoing HTTP requests"` synchronously (via `bios.lua`), and `http.request` queues an `http_failure` event consistently with the pre-existing URL-rejection path (no double events — the locked re-check cancels before adding to the list). The whitelist/blacklist matching is a shared `matchesDomain(host, list)` helper with identical regex semantics to the pre-existing whitelist check. This closes the thread/memory DoS vectors (item 3 in the priority list); the shared `ExecutorService` and non-zero default timeout follow-up (P2) is also done. Covered by `src/test/java/dan200/computercraft/core/apis/HTTPLimitsTest.java` (17 tests: blacklist rules for http + websockets, request cap incl. `0`-means-unlimited, download-limit abort/success against a local in-process `HttpServer`, and the P2 executor/timeout tests).

### S3 🔴 `NBTUtil` event encoding bugs — ✅ **FIXED**
`shared/util/NBTUtil.java`:

* **Line 47 (was):** `NBTBase value = toNBTTag(entry.getKey());` — the *key* was encoded as the *value*. Any table passed through `ClientComputer.queueEvent` → packet → `ServerComputer.handlePacket` (e.g. `os.queueEvent("x", {{a=1}})` triggered from a client GUI path) arrived with all values replaced by their keys. Verified identical in the original dan200 source — an upstream bug.
* **Line 215 (was, `decodeObjects`):** `Object[] objects = new Object[len];` where `len` is read from client-supplied NBT → a modified client could trigger `new Object[Integer.MAX_VALUE]` → OOM. Same class of bug as S1.
* **Line 55 (was):** `nbt.setInteger("len", m.size())` counted entries that may have been skipped (unencodable key/value), desynchronizing encode/decode.
* `byte[]` (Lua binary strings) were not encodable and were silently dropped from client→server event arguments.

**Fixed (2026-06):** `toNBTTag` now encodes `entry.getValue()` (the key/value bug); the map `len` is derived from the entries actually written so encode→decode is lossless even when entries are skipped; `byte[]` values are encoded as `NBTTagByteArray` (and decoded back) in both the event path and inside nested maps; `fromNBTTag` gains byte array decoding; and hostile lengths are clamped — `decodeObjects` rejects `len` outside `1..256` (returning null) and nested maps reject `len` outside `0..4096` (returning null) instead of allocating attacker-sized structures. Covered by `src/test/java/dan200/computercraft/shared/util/NBTUtilTest.java` (16 tests: scalars, map key/value correctness, nested maps, skipped unencodable entries, byte[] in args and in maps, hostile top-level and nested lengths, plus `toObject` tile-entity sanity).

### S4 🟠 Malformed packet → unvalidated array access (server noise) — ✅ **FIXED**
`shared/proxy/ComputerCraftProxyCommon.handlePacket` (cases 1–6: `packet.m_dataInt[0]`) and `ServerComputer.handlePacket` (case 4: `packet.m_dataString[0]`) index packet arrays without length/null checks. A modified client sending a type-4 packet with no strings causes NPE/AIOOBE. `PacketHandler` catches `Exception`, so it's log spam rather than a crash — but it should be validated.

**Fixed (2026-09):** `ComputerCraftPacket` gains two payload-shape predicates — `hasInts(count)` and `hasStrings(count)` (the latter requires non-null elements) — and every indexed access in the packet handlers is now guarded behind them: `ComputerCraftProxyCommon.handlePacket` cases 1–8 (instance lookup), case 9 (`RequestTileEntityUpdate`, 3 ints), `SpeakerAudio` (4 ints) and `SpeakerStop` (3 ints), plus `ServerComputer.handlePacket` case 4, which now also refuses to queue an event whose name string is null (network-decoded packets can carry null string elements). Malformed packets are dropped silently — consistent with the pre-existing `computer != null` drop — so a hostile client produces no exception or log spam. Legitimate flows are preserved (e.g. `SetLabel` still tolerates a null string to clear the label). Covered by `src/test/java/dan200/computercraft/shared/computer/core/ServerComputerPacketGuardTest.java` (5 tests: malformed/valid `QueueEvent` packets against a real `ServerComputer`, payload-less control packets, and the `SetLabel` set/clear flow) and 4 new predicate/decode tests in `ComputerCraftPacketTest`.

### S5 🟠 ChatBox impersonation & CNPC command execution (admin-facing)
* `ChatBoxPeripheral.say/tell` format messages as `[<label>] <text>` where `<label>` is a free-form ≤32-char string — a computer can convincingly impersonate `[Server]` or another player, and with the default `chatbox_max_range = -1` broadcast to every player in every dimension. No permission gate exists. Consider a config option to force a fixed prefix or to require the label to differ from player names.
* `NpcInterfacePeripheral.executeCommand` / `TraderRolePeripheral` rely on CustomNPCs' `npc.executeCommand`, which executes with NPC (op-level) permissions. Any player who can place an `npc_interface` can run op-level commands through a computer. This mirrors what CustomNPCs itself allows, but it deserves a loud note in `docs/CUSTOMNPCS_INTEGRATION.md` and possibly an opt-in config.
* `SpeakerPeripheral.playSound` accepts arbitrary sound names (≤512 chars) — harmless in vanilla but a nuisance vector; volume is properly capped at 3.

## 2. Functional bugs

### B1 🟠 `buffer` API is dead code **and** broken — ✅ **FIXED (deleted)**
* `core/apis/BufferAPI.java` is never registered — no `new BufferAPI(...)` exists outside the class itself, and `Computer.createAPIs()` doesn't add it. The `buffer` row in `docs/TWEAKEDCC_COVERAGE.md` therefore overstates coverage: the API is not reachable from Lua.
* If it were registered:
  * **Line 88 (`read`):** `startxx = ((Number) arguments[1]).intValue() - 1;` — the guard validates `arguments[0]` but reads `arguments[1]`. `buf:read(5)` throws AIOOBE (`Java Exception Thrown`); `buf:read(1, 5)` silently uses the *end* index as the start.
  * **Line 148 (`fill`) + `TextBuffer.fill(String,...)`:** `fill("")` on a non-empty buffer reaches `text.charAt((i - pos) % textLength)` with `textLength == 0` → `ArithmeticException: / by zero`.

**Resolved (2026-09): deleted.** Investigation showed the `buffer` API is *not* a CCTweaks feature — it appears nowhere in the vendored `migrate/CCTweaksSourceCode` tree, CCTweaks' README only advertises the `socket` and `data` APIs, and CC:Tweaked has no `buffer` global either. It was an unfinished hand-written idea from the migration that was never wired up, so `BufferAPI.java` was deleted and the bogus `buffer` row removed from `docs/TWEAKEDCC_COVERAGE.md` (no Lua-visible change: the API was unreachable). The `fill("")` div-by-zero lives in `TextBuffer` itself, which *is* live code (used by `Terminal` for colour rows), so both `fill(String,...)` and `fill(TextBuffer,...)` overloads now treat an empty pattern as a no-op instead of dividing by zero. Today's `Terminal` callers can't trigger it (they always fill single-char strings with `end == start + 1`), but it is now impossible to hit from any future caller. Covered by the new `src/test/java/dan200/computercraft/core/terminal/TextBufferTest.java` (9 tests: empty-pattern fills via both overloads and the one-arg overload, tiling/bounds/clamping of `fill`, `write`/`read` basics, and the repeating constructor).

### B2 🟠 `OSAPI.Alarm.compareTo` compares `this` with `this` — ✅ **FIXED**
`core/apis/OSAPI.java:549`: `double ot = this.m_day * 24.0 + this.m_time;` — should be `o.m_day * 24.0 + o.m_time`. Currently, always returns 0. Latent only (alarms live in a `HashMap` and are never sorted), but the class implements `Comparable` for no reason — fix or delete `compareTo`.

**Fixed (2026-09):** `compareTo` now folds the *other* alarm's day and time into the ordering key (`o.m_day * 24.0 + o.m_time`), so `Alarm` finally implements the `Comparable` contract it declares. No behavioural change in game today — alarm firing compares absolute times directly in `OSAPI.advance()` and the map is never sorted — but any future sorted structure (e.g. a `PriorityQueue` of alarms) would silently have mis-ordered alarms. Covered by 3 reflection-based regression tests in `OSAPITest` (same-day ordering in both directions, cross-midnight day-boundary ordering where a plain time-of-day comparison would be wrong, and equality/reflexivity) — all of which fail with the old always-0 implementation.

### B3 🟡 `TurtleBrain.setOverlay` compares the wrong field — ✅ **FIXED**
`shared/turtle/core/TurtleBrain.java:613`: `!Objects.equal(this.m_hatOverlay, overlay)` — second comparison should use `hatOverlay`, not `overlay`. Effect is only a spurious `updateBlock()` (state itself is written correctly), but it's a real copy-paste bug.

**Fixed (2026-09):** the second comparison now tests `m_hatOverlay` against the `hatOverlay` argument. The bug was slightly worse than "spurious `updateBlock()`": whenever both fields already equalled the new body overlay (`m_overlay == overlay == m_hatOverlay`), the whole condition was false and a hat-only change was **silently dropped**. Covered by `src/test/java/dan200/computercraft/shared/turtle/core/TurtleBrainOverlayTest.java` (3 tests against a real `TileTurtle` with a mocked `World`, since `TileGeneric.updateBlock()` is final): changed values update fields + fire exactly one block update, an identical re-set is a no-op (the spurious-update regression, fails with the bug when the two overlay textures differ), and a hat-only change is applied (the dropped-change regression, also fails with the bug).

### B4 🟡 `fs.open` error contract is inconsistent — ✅ **FIXED**
`core/apis/FSAPI.java` case 11: modes `r`/`w`/`a`/`rb`/`wb`/`ab` return bare `nil` on `FileSystemException`, while `r+`/`w+` return `nil, message`. CC:T returns `nil, "message"` for all modes. Programs that surface the second return value get no diagnostic for the common modes.

**Fixed (2026-09):** mode dispatch moved out of `callMethod` into `FSAPI.openFile(path, mode)`, and all eight modes now share the single CC:T contract — handle on success, `nil, message` on failure. `FileSystem`'s open methods are documented to return `null` (rather than throw) when there is nothing to open, and every one of those paths was wrapped anyway: `fs.open("ghost", "r")` against such a mount returned a *handle* whose first `read`/`write` threw an uncaught `NullPointerException` in the computer's coroutine — those `null` returns are now rejected with `No such file` (read modes) or `Failed to open file` (write modes). A `FileSystemException` carrying no message (possible whenever the wrapped `IOException.getMessage()` is null) yields `Could not open file` instead of the string `"null"`. `Unsupported mode` remains a Lua *error* (unchanged), which is what `rom/apis/io` pre-validates around. Two ROM follow-ups make the diagnostic visible to programs: `io.open` now passes `fs.open`'s reason through instead of replacing it with `"Failed to open file"` (its `or` fallback still covers message-less handles), and `rom/help/fs` documents the contract. Note the fix is source-compatible for Lua: `local f = fs.open(...)` is unaffected, and `cc.image.nft.load` — which already reads the second return value — now gets a real reason. Covered by 9 new tests in `src/test/java/dan200/computercraft/core/apis/FSAPITest.java` (missing file for `r`/`rb`/`r+` → `No such file`; write modes + `r+`/`w+` on a read-only mount → `Access Denied`; directories → `Cannot write to directory` / `No such file`; mounts that hand back a `null` read/write handle; the message-less fallback; success returns *exactly one* value for all eight modes and closes cleanly; `Unsupported mode` still throws) and one in `IOAPITest` (reason pass-through). 8 of the 10 fail against the previous implementation (7 with the old `FSAPI`, 1 with the old `io`); the other 2 pin the behaviour that must *not* change.

### B5 🟡 `http.get`/`http.post`/`http.websocket` in `bios.lua` can steal each other's events — ✅ **FIXED (completion correlation)**
`bios.lua` previously matched completion events by URL only (`param1 == _url`). Concurrent requests to the *same* URL, or concurrent WebSocket connection attempts to the same URL, could return another call's response/error. This fix uses internal request IDs; it does not depend on the report's previously unverified claim about how CC:T addressed the issue.

**Fixed (2026-09):** the synchronous wrappers allocate monotonically increasing IDs from a shared BIOS-local counter and pass them as optional trailing native arguments (`request` argument 7, `websocket` argument 3). `HTTPRequest` and `WebSocketRequest` retain the ID, and `HTTPAPI.advance()` appends it to completion events. The wrappers require both URL and ID to match, including out-of-order success/failure delivery and failures with no response handle. Existing event arguments retain their positions: tagged HTTP success is `(url, response, id)`, tagged HTTP failure is `(url, error, responseOrNil, id)`, and tagged WebSocket success/failure is `(url, handleOrError, id)`.

**Compatibility and scope:** `http.request` and `http.websocketAsync` remain untagged and retain their existing event shapes; existing Java constructors also remain available and untagged. Immediate synchronous rejection returns directly (`nil, error` for HTTP; `false, error` for WebSocket) without waiting or queuing a synthetic failure that another caller could consume. Async rejection still queues its legacy failure event. Unrelated events are still discarded by the waiting coroutine, not buffered/replayed (legacy semantics, see C5); `rom/help/http` now recommends `parallel` or an asynchronous event loop when other events must be handled. This fixes **connection/request completion**, not WebSocket message/close routing: `WebSocketHandle.receive` and message/close events still identify connections by URL, so receiving from multiple sockets to one URL remains a separate limitation.

**Tests:** four new tests in `src/test/java/dan200/computercraft/core/lua/HTTPAPITest.java` exercise same-URL GET/POST and WebSocket coroutines with out-of-order success/failure events, rejection of untagged/other-URL events, immediate rejection, unchanged async behavior, and termination. Existing wrapper tests now model the native ID echo and explicitly preserve nil event slots. `src/test/java/dan200/computercraft/core/apis/HTTPRequestCorrelationTest.java` checks tagged/untagged completion shapes, nil response slots, native argument forwarding, exactly-once emission, and constructor compatibility using a local HTTP server and mocked completion state. Validation: all 1,245 tests passed (including 17 Lua HTTP wrapper tests and 14 Java correlation cases). Removing the four BIOS ID comparisons makes both same-URL concurrency regressions fail; restoring them passes.

### B6 🟡 `FileMount` can NPE on unreadable directories — ✅ **FIXED**
`core/filesystem/FileMount.java` `list()` and `deleteRecursively()` iterate `file.list()`, which returns `null` on I/O error → NPE (uncaught, kills the computer's coroutine with a Java exception). Add a null guard → `IOException("Access denied")`.

**Fixed (2026-09):** every `File.list()` result in `FileMount` is now null-guarded. `list()` and `deleteRecursively()` raise `IOException("Access denied")` (matching this class's existing denial message, so `fs.list`/`fs.delete` report a normal error instead of killing the coroutine); `measureUsedSpace` cannot throw (`IOException` is not declarable from the constructor) so an unreadable subdirectory is accounted for as that directory alone rather than aborting construction of the mount. Covered by the new `src/test/java/dan200/computercraft/core/filesystem/FileMountTest.java` (7 tests: `list` on an unreadable directory → `Access denied` with nothing appended, and on a plain file → `Not a directory`; `delete` on an unreadable directory → `Access denied` with the space accounting unchanged; `measureUsedSpace` via reflection on an unreadable directory; plus happy-path `list` and used-space accounting so the guards cannot silently mask working behaviour). A `null`-listing `File` does not occur portably on a real filesystem, so the tests inject a `File` stub through `getRealPath` (and via reflection for the constructor path). Mutation-checked: removing the guards fails all three unreadable-directory tests with the original NPE.

### B7 🟡 `JarMount.m_root` can remain null → NPE on first use — ✅ **FIXED**
`core/filesystem/JarMount.java` — if the zip contains the sub-path but never yields an exact root entry, `m_root` stays null and `exists()` NPEs. Guard with an `IOException("Zip does not contain path")`.

**Fixed (2026-09):** three related defects were addressed in the constructor. (1) **Null root**: if no entry resolves to the mount root, the constructor now closes the `ZipFile` (no handle leak) and throws `IOException("Zip does not contain path")` instead of leaving `m_root == null` for the first `exists()`/`list()` call to NPE on. (2) **Enumeration-order dependence**: children were previously attached only when they happened to be enumerated *after* the root entry, so any child listed first was silently dropped (and a nested child whose parent entry came later was dropped too). Children are now collected during the scan and attached once the root is known, sorted by path depth so intermediate directories always exist before their contents. (3) **Prefix siblings**: the old `entryName.startsWith(subPath)` check also matched unrelated siblings such as `"romario/fake.txt"` for `"rom"`, which was handed to `FileSystem.toLocal` — tripping its `assert contains(location, path)` (an `AssertionError` with assertions enabled, a silently mis-pathed entry without), so containment is now `equals(subPath)` or `startsWith(subPath + "/")`, matching `FileSystem.contains` exactly. Honest scope note: after (3), the (1) guard is defence-in-depth — the reachable null-root triggers were the mis-parsed prefix siblings, and the tests pin the no-NPE contract rather than reproducing the old crash. Covered by the new `src/test/java/dan200/computercraft/core/filesystem/JarMountTest.java` (9 tests: children enumerated before the root are still mounted; deep children attach parents-first regardless of order; prefix siblings are excluded; missing sub-path / missing jar / corrupt archive all raise `IOException` or `FileNotFoundException` as documented; reading a valid mount; a root that is a file entry; and clean `No such file`/`Not a directory` errors for absent entries). Mutation-checked: restoring `startsWith` fails `prefixSiblingsAreNotMounted` with the `toLocal` `AssertionError`, and disabling the deferred attach fails the two ordering tests. The tests also release each mount's `ZipFile` in `@AfterEach` (via reflection) because `JarMount` exposes no `close()` and Windows otherwise blocks JUnit's temp-directory cleanup.

### B8 🟡 `FileSystem.getFreeSpace` is the only unsynchronized public FS method — ✅ **FIXED**
`core/filesystem/FileSystem.java:822` — every other public method is `synchronized`; this one isn't. Benign in practice (reads a long), but inconsistent.

**Fixed (2026-09):** `getFreeSpace` is now `synchronized` like its siblings (`getCapacity`, `getAttributes`, `exists`, …), closing the last mount-tree access path that could observe a mount being swapped by `mount`/`unmount` mid-call. An audit of the class confirmed the remaining unsynchronized public methods are intentionally so: `addFile`/`removeFile`/`unload` (open-handle bookkeeping, called from per-handle threads) and the pure path helpers `getName`/`contains`/`getDirectory`/`toLocal` (no mutable state). Covered by the new `src/test/java/dan200/computercraft/core/filesystem/FileSystemSyncTest.java` (4 tests: a reflection audit asserting every public method outside the intentional set stays `synchronized` — it fails listing `getFreeSpace` if the modifier is removed again — an explicit `getFreeSpace` modifier check, free-space accounting through a `FileSystem` write, and a 6-reader + 1-mutator hammer of `getFreeSpace`/`getCapacity`/`exists` against `makeDir`/`delete` churn asserting no exception or deadlock).

### B9 🟡 `TermAPI` colour getters read without the terminal lock — ✅ **FIXED**
`core/apis/TermAPI.java` cases 14–17 (`getTextColour`/`getBackgroundColour`) read terminal state without `synchronized(m_terminal)` while every writer locks it. Benign today (single computer thread + client sync thread) but a latent race.

**Fixed (2026-09):** cases 14–17 (`getTextColour`/`getTextColor`/`getBackgroundColour`/`getBackgroundColor`) now read `m_terminal` under `synchronized(m_terminal)`, matching every other accessor in the class, so a cursor-colour change can no longer interleave with a getter read (relevant with the P1 worker pool now able to run a computer's tasks while client sync reads the same terminal). Covered by 3 new tests in `TermAPITest`: defaults and a write→read round-trip through both the American and British spellings (also pinning that the getters return the `1 << index` bitmask `encodeColour` produces), and a 4-reader-thread hammer asserting concurrent getter calls against 2,000 colour flips only ever observe one of the two exact bitmasks being written — never a torn combination.

### B10 🟡 `term.blit` doesn't validate color characters — ✅ **FIXED**
`core/apis/TermAPI.java` case 18 checks only that the three strings are equal-length. `term.blit("x", "g", "0")` writes an invalid color char into the buffers. `FixedWidthFontRenderer` clamps invalid indices to color 15/0 so there is **no crash**, but the data is garbage and `term.getPaletteColor`/NBT round-trips carry it. CC:T rejects with `Invalid colour`. Cheap hardening: validate `textColour`/`backgroundColour` against `[0-9a-f]` in `TermAPI.blit` (mirroring the renderer's `"0123456789abcdef".indexOf` logic).

**Fixed (2026-09):** `TermAPI.checkColour(String)` validates every character against `0123456789abcdef`. Both native `term.blit` and `monitor.blit` validate both colour strings after the existing type/length checks and before touching the terminal, throwing `LuaException("Invalid colour")`. Rejection leaves all three buffers, the cursor and the changed flag untouched, even for off-screen or clipped blits. All 16 lowercase hex characters and empty strings remain valid; text itself is unrestricted. This prevents invalid blit data entering terminal buffers and subsequent NBT snapshots (palette getters are separate and were never affected). The ROM `window` API is unchanged: it maintains its own buffers, so window-side validation is a separate follow-up rather than a consequence of this native API guard. Covered by 5 new tests in `TermAPITest` (9 invalid characters in each colour argument with no state mutation; full-alphabet acceptance and cursor advance; empty strings; clipped/off-screen validation; preserved type/length errors) and 3 in `MonitorPeripheralTest` (invalid inputs, including the exact B10 reproduction, rejected before terminal access; existing error contracts; shared validator alphabet).

### B11 🟡 `HTTPRequest` writes `responseCode`/`responseMessage` outside its lock — ✅ **FIXED**
`core/apis/HTTPRequest.java` — the worker thread assigns `responseCode`/`responseMessage` without holding `lock` while `asResponse()` reads them under it. Practically safe because `complete` (volatile-ish via the lock) is set last, but the fields should be assigned inside the synchronized block for clarity/consistency (inherited from upstream).

**Fixed (2026-09):** the status pair is now read from the connection into locals and assigned inside `synchronized (lock)`, so whoever first observes a completed request is guaranteed to observe its status as well; a comment on the fields records the invariant. The rest of the class was already correct — `complete`, `cancelled`, `success`, `result`, `responseHeaders`, `failureReason` and `m_workerThread` are all written under the same lock, so these two fields were the only offenders. Two things learned while testing, both now written down rather than "fixed" twice: `HttpURLConnection.getResponseMessage()` really can return `null` (verified on JDK 8 *and* 21 against a status line with no reason phrase), and `HTTPResponse` already normalises it to `""` at the Lua boundary — so the normalisation stays in that one place. Being straight about severity: the pre-fix code cannot be made to misbehave on the hardware we run on (HotSpot/x86 publishes stores in program order and `complete` is set afterwards), so this closes a JMM gap rather than a live bug — the new tests are guards, not reproductions, and the test class says so. Covered by `src/test/java/dan200/computercraft/core/apis/HTTPRequestStatusTest.java` (6 tests, all against an in-process `HttpServer` plus one raw `ServerSocket` for the phrase-less status line): success publishes code + reason + headers; a 404 publishes them too while still honouring the 1.80pr1 "error status still yields a handle" contract; a bare `HTTP/1.1 200` status line reaches Lua as `""` and never `null`; a refused connection and a request cancelled while queued yield *no* handle (so no half-published `(-1, "")` sentinel either); and 24 concurrent requests polled by 4 reader threads never see a partial or mismatched pair. Mutation-checked: deleting the publication fails the success test, and publishing only on the 2xx/3xx path fails the 404 test.

### B12 🔵 Known legacy limitations (document, don't necessarily fix)
* Dropped file handles are only reclaimed on computer unload — a Lua program that discards handles without `close()` leaks them until shutdown (bounded by `maxFilesHandles`).
* `os.pullEvent(filter)` semantics: `CobaltMachine.handleEvent` drops events that don't match the coroutine's filter, matching CC 1.7.10. Modern CC:T queues them in the bios. Any ported CC:T program relying on non-consuming filtered pulls will lose events.
* `WebSocketHandle.receive` (core/apis/WebSocketHandle.java) loops on `pullEventRaw(null)` and discards all events that aren't for its URL — consistent with the above, but the strongest event-loss case; consider documenting or queueing non-matching events.
* `modem.transmit` payload size is unbounded (a Lua program can stuff a multi-MB table through rednet).
* `JarMount` opens a `ZipFile` and never closes it: `IMount` has no lifecycle/`close()` hook, and the mounts are created once per resource pack at startup and live for the process lifetime. Harmless in game, but it means the jar handle stays open (tests that build throwaway jars must release it explicitly — see `JarMountTest`).

## 3. Concurrency & threading

### C1 🟠 `ComputerThread.queueTask`: unsynchronized `WeakHashMap` access — ✅ **FIXED**
`core/computer/ComputerThread.java:136` — `m_computerTasks.get/put` (a `WeakHashMap`) is executed without any lock while being called from **multiple threads** (server thread, HTTP worker threads, WebSocket threads, CNPC event dispatch). `WeakHashMap` is not thread-safe: concurrent access can corrupt internal state or throw. Verified inherited from the original (the upstream code is identical). Wrap the get/put in `synchronized(m_lock)` (or use `ConcurrentHashMap` keyed by computer ID).

**Fixed (2026-09):** the `get/put` pair in `queueTask` is now atomic under `m_lock` (the same lock `start()`/`stop()` use; the critical section is a map probe, so contention is negligible). The `WeakHashMap` was kept deliberately — its weak keys are load-bearing (an unloaded computer's lane becomes collectible), which a `ConcurrentHashMap` cannot replicate without leaking lanes. No lock-ordering hazards: `m_lock` is never held nested with the lane lock (`m_ready`) — `queueTask` releases it before touching the lane — and the P1 rewrite kept that discipline. While writing the tests, a closely related latent bug surfaced and was fixed in the same class: `start()`'s fresh-thread branch did not clear `m_stopped`, so a restart after `stop()` (e.g. reloading a world in the same JVM) spawned a dispatch thread that inherited the previous stop request and exited on the first queued task — silently killing all computer execution. Covered by the new `src/test/java/dan200/computercraft/core/computer/ComputerThreadTest.java` (6 tests: 8 producer threads × 16 tasks hammering the shared default-lane key with exactly-once execution verified, `start()`-after-`stop()`, full-queue drop reporting, and the P1 pool semantics).

### C2 🟠 Silently dropped events when a computer's queue is full — ✅ **FIXED**
`ComputerThread.java:142` — `queue.offer(_task)` on the 256-cap queue: when full, the task is **silently discarded** (upstream had a commented-out `// Event queue overflow`). A spammy computer (or fast event source) can drop `terminate`/`redstone`/`peripheral` events invisibly. Consider `put()` (blocking is fine — the producer is usually the main thread... verify) or at least log at debug level.

**Fixed (2026-09):** the producer question is now answered: `queueTask` is called from the server main thread *and* HTTP workers, websocket threads, and CNPC dispatch, so blocking with `put()` is the wrong fix — a wedged computer (queue full while the dispatcher is stuck in `worker.join(computerThreadTimeout)` = 7s on one task) would freeze the server main thread for up to ~10s per overflow. Instead, the drop is made **loud and observable**: `queueTask` now returns `boolean` (`false` = dropped), every drop logs at DEBUG with the owning computer's ID, and a throttled WARN (max once per 5s) reports the aggregate drop count so a flooding computer shows up in the log instead of vanishing. The drop accounting lives under the `ComputerThread` lane lock, and a full lane is always already tracked as ready or busy, so it needs no re-registration. Existing callers are unaffected (they ignore the return value). Covered by `queueTaskReportsDropsWhenTheQueueIsFull` in `ComputerThreadTest`: a worker is deterministically parked on a latch task (which marks its lane as serviced, so nothing can drain it), the lane is filled to exactly its 256 capacity, the overflow offer and a follow-up offer both report `false`, and after release all 257 accepted tasks execute exactly once — proving the drop doesn't disturb the pipeline.

### C3 🟡 `Computer`'s `ITask.execute` bodies synchronize on the *task object* — ✅ **FIXED**
`core/computer/Computer.java` (`startComputer`/`stopComputer`/`queueEvent` anonymous tasks) used `synchronized(this)` where `this` was the anonymous `ITask` — each task locked a unique object, providing **no mutual exclusion** against main-thread state transitions (`advance()`, `unload()` lock the `Computer`). Verified identical in the original dan200 source, so this was an inherited hazard rather than a decompiler artifact. Correction to the original report: `api.advance()` and `api.shutdown()` already shared the `m_apis` lock, so overlapping those callbacks was not a valid reproduction. The actual missing guarantee was coordination of task-side lifecycle/state access with the Computer monitor.

**Fixed:** startup and shutdown lifecycle sections and the queued-event state recheck now synchronize on `Computer.this`. This is deliberately **not** a blanket replacement around Lua execution: startup's first `handleEvent(null, null)` now runs outside the Computer monitor (as subsequent event resumes already did), allowing the watchdog's `abort()` and server ticks to acquire it while Lua runs. Per-computer task lanes still serialize machine execution and unload. `isBlinking`, `getRedstoneOutput`, and `getBundledRedstoneOutput` now acquire Computer **before** terminal/output, removing their reverse lock order relative to lifecycle tasks.

**Tests:** `src/test/java/dan200/computercraft/core/computer/ComputerLockTest.java` adds 7 tests covering startup/shutdown monitor ownership, `advance()` waiting for shutdown, stale queued events rechecking state under the Computer lock, reboot, getter lock order, and abort/tick access during first and subsequent Lua resumes. Startup uses a real Cobalt machine with `src/test/resources/computer-lock-test-bios.lua`; other tests inject a mocked machine to isolate lifecycle behavior. Mutation check: restoring the three task-object locks fails 4 targeted tests. Validation: all **1,252 tests pass** with the fix restored. Repository-wide `spotlessCheck` remains blocked by pre-existing formatting violations in unrelated test files; incidental formatting of those files was reverted to keep this change scoped.

### C4 🟡 `ComputerThread.stop()` doesn't stop an idle dispatch thread — ✅ **FIXED (in the P1 rewrite)**
When the dispatcher is waiting on `m_monitor`, `interrupt()` wakes it, the `InterruptedException` is swallowed, and it re-enters `wait()` — `m_stopped` is never re-checked in the idle path. Harmless today (one thread, restarted flag semantics), but the stop contract is broken. Also `m_busy` (line 19) is written twice and never read — dead field; remove.

**Fixed (2026-09)** as part of the P1 worker-pool rewrite: the idle path now re-checks `m_stopped` and the pool-generation token on every wakeup, `stop()` explicitly `notifyAll()`s the workers' monitor, workers/watchdog are daemon threads (so forgetting to stop can no longer pin the JVM), the dead `m_busy` field is gone, and `start()` after `stop()` no longer spawns threads that instantly exit — covered by `startAfterStopRunsNewlyQueuedTasks` in `ComputerThreadTest`.

### C5 🔵 Event filter semantics (see B12) — the machine drops non-matching events; this is the *legacy* contract and is implemented faithfully by `CobaltMachine.handleEvent`.

### C6 🔵 Client packets mutate the terminal on the netty thread
`PacketHandler.onClientPacket` → `ClientComputer.handlePacket` → `readDescription`/terminal writes happen on the network thread while the render thread reads the same `Terminal`. Legacy behavior; no corruption observed in practice, but a `synchronized(terminal)` in `ClientTerminal.readDescription` would be cheap insurance.

## 4. Performance

### P1 🟠 Global serialization + thread-per-task computer execution — ✅ **FIXED**
`ComputerThread`'s dispatch loop `take()`s one task, **spawns a new `Thread`**, and `join(timeout)`s it. Consequences:
* All computers on the server execute strictly one-at-a-time (single lane). A single busy computer delays every other computer's event handling by up to `computerThreadTimeout` (7 s) if it wedges.
* Thread creation per task is expensive at high event rates (timer-heavy programs, rednet storms).

CC:T's answer is a fixed worker pool with per-computer queues. Even a modest change (2–4 worker threads with per-computer task lanes, still serialized *per computer*) would materially improve multi-computer servers. This is the fork's biggest scalability lever.

**Fixed (2026-09):** `ComputerThread` was rewritten as a fixed worker pool with per-computer lanes:

| Before | After |
|---|---|
| 1 dispatch thread, tasks run strictly one-at-a-time globally | `computerThreads` workers (new config option, default **4**, min 1) |
| `new Thread(...)` + `join(timeout)` per task | tasks execute **in the worker thread** — no thread creation per task |
| timeouts enforced by the dispatcher blocking in `join` | dedicated **watchdog thread** (50 ms tick) applying the same abort ladder per lane |
| a wedged computer stalls *every* computer for up to ~10 s | a wedged computer stalls only its own lane; other computers keep running |

Semantics preserved deliberately: tasks of one computer still run **strictly serially** (a lane being serviced is excluded atomically, so the Lua machine of a computer is only ever touched by one thread), the abort escalation is unchanged (soft abort at `computerThreadTimeout` → hard abort +1.5 s → runner interrupt +1.5 s), the 256-per-computer queue cap and C2 drop reporting are kept, and the lane map is still a `WeakHashMap` under `m_lock` (C1) so unloaded computers' lanes are collectible. Two robustness changes came with the rewrite: workers/watchdog are **daemon** threads (no production path calls `stop()`, so the old non-daemon dispatch thread could only ever be reaped by `System.exit`), and a **pool-generation token** makes stragglers from a stopped pool exit even if `start()` immediately clears the stop flag. Covered by 3 new tests in `ComputerThreadTest`: `tasksForDifferentComputersRunConcurrently` (three computers' tasks must all be running at once — impossible under the old single lane), `tasksForTheSameComputerRunSerially` (a second task for a busy computer must not start while other workers are idle), and `watchdogInterruptsARunawayTaskAfterTheEscalationLadder` (with a 200 ms timeout, the runner is interrupted ~3.2 s later, proving the rewritten timeout enforcement still terminates runaway tasks).

### P2 🟠 Thread-per-HTTP-request — ✅ **FIXED**
`HTTPRequest` and the (removed) per-request thread model: replace with one shared bounded `ExecutorService` (see S2). Also caps naturally fall out of a bounded pool.

**Fixed (2026-09):** `HTTPRequest` no longer spawns a fresh thread per request; every request is submitted to one **shared, bounded executor** shared by all computers, sized by a new `http_threads` config option (default **8**, min 1, daemon threads named `computercraft-http-N`). Requests above the pool size are queued in the executor until a thread is free (per-computer in-flight counts are still capped by `http_max_requests`), so a fleet of computers can no longer multiply into hundreds of concurrent HTTP threads. Two changes ride along:

* **`http_timeout` (default 30000 ms, `0` = none)** — the action list's "non-zero default timeout" follow-up. With a bounded pool, a request to a hung server would permanently consume one of the pool's threads (16 such requests starve HTTP for *all* computers), so requests without an explicit Lua timeout argument now default to the configured timeout and surface a normal `http_failure`. Lua programs that pass their own timeout are unaffected.
* **Cancel-before-start guard** — with a queue it is now possible for a request to be cancelled (`http_max_requests` race loser, or `shutdown()`) *before it starts running*. The task now checks the cancelled flag before opening any connection instead of dutifully connecting to a server it will never report to.

The pool is rebuilt if the configured thread count changes, and existing behaviour (whitelist/blacklist, download limit, response handles, error-code bodies) is untouched. Covered by 4 new tests in `HTTPLimitsTest`: `requestsRunOnABoundedReusedThreadPool` (6 requests served by ≤ 2 named `computercraft-http-*` threads via a new package-private `HTTPRequest.getWorkerThread()` hook — thread-per-request would show 6), `executorBoundsConcurrentRequests` (max handler concurrency ≤ pool size), `cancelledQueuedRequestNeverConnects` (a queued-then-cancelled request behind a blocked pool thread never reaches the server), and `defaultTimeoutAbortsSlowRequests` (a request with no Lua timeout aborts after the configured 300 ms instead of hanging for the server's 5 s).

### P3 🟡 Terminal sync broadcasts full state to *all* players
`ServerComputer.broadcastState()` → `ComputerCraft.sendToAllPlayers(packet)` with the **entire terminal NBT** (every line ×3 text buffers + palette) on every change. With many active computers/monitors this dominates bandwidth. Improvements (in order of value): (a) send only to players tracking the chunk, (b) diff-based terminal updates (CC:T-style), (c) skip the 3× per-line strings when only the cursor blinked.

### P4 🟡 CNPC entity lookups are O(all loaded entities) per call
`NpcInterfacePeripheral.resolveByUUID`, `TileNpcInterface.resolveByUUID/resolveNpcs`, and `NpcDetectorPeripheral` (name/UUID paths) iterate `api.getLoadedEntities()` linearly, **across all dimensions**, for every Lua call. On a busy server with thousands of entities, `getName()`-style polling loops (the documented pattern for `npc_trader`) become expensive. Options: cache a `Map<uuid, ICustomNpc>` refreshed per tick, or use `IWorld.getEntitiesNear` with the position (the detector's spatial methods already do this correctly).

### P5 🟡 URL whitelist patterns are recompiled per request
`HTTPRequest.checkURL`/`checkWebSocketURL` call `Pattern.compile` for every whitelist entry on every request. Parse the config once into a `Pattern[]` at startup.

### P6 🟡 Wired network BFS on every transmit
`TileCable.dispatchPacket` runs a full BFS (`searchNetwork`, 256-block radius) for **every modem message**, and `findPeripherals` repeats it on every network change. Legacy behavior; fine for small networks, scales poorly for big cable farms. A per-network receiver index (like `WirelessNetwork`'s channel map) would remove the BFS from the hot path.

### P7 🔵 Minor
* `FixedWidthFontRenderer.getIndex(char)` does a linear scan over a 256-char string per glyph — precompute a `char → index` lookup table at font load.
* `HTTPResponse.readLine` scans with `Arrays.copyOfRange` per line — fine, but a shared `ByteArrayInputStream`-style cursor would avoid copies.
* `FileSystem` contains four near-identical copies of the `readLine`/`seek` handle implementations (read, read-write, read-seekable RAF, read-seekable stream, write-seekable) — extract a shared base class; ~200 lines saved and one place to fix bugs.
* `FileSystem` tracks `m_openFiles` (HashSet) *and* `openFilesCount` (int) — redundant; use the set size.
